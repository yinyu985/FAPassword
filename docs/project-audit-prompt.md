# FAPassword 项目自检提示词

将下面的内容交给能读取本仓库的代码审查助手。目标是发现值得做的改进，不是凑够问题数量。默认只审查，不改产品代码。

## 第一遍：从用户动作追到实现

1. 以当前工作树为准。先看 `git status --short`，列出已跟踪文件和未跟踪但未忽略的文件，区分已删除的旧测试、实际源码、生成的 bundle 和 dist。不要还原用户的修改。读 `SPEC.md`、双语 README、manifest、npm scripts、CI 和构建白名单，画出实际交付边界。
2. 从安装、首次启动、聚焦字段、列出账号、分步填充、生成、手动保存、可选自动保存、解锁、刷新、再次填充、改设置到卸载逐项追踪。每条路径记录：谁触发、在哪个进程执行、需要哪些权限、会读什么数据、写到哪里、用户看见什么。特别检查“未操作”“已取消”“功能关闭”时不会发生什么。
3. 从 `content.js`、`popup.js` 沿消息追到 `background.js`、`protocol.js` 和原生助手；反向检查响应最终进了哪个 tab/frame/document/字段。区分扩展自身决策、浏览器限制和 Apple 系统行为。不要只读函数名或注释。

## 第二遍：用失败场景挑战第一遍的结论

| 维度 | 必查内容 |
|---|---|
| 用户授权与隐私 | 登录≠保存，开弹窗≠解锁，只填账号≠读密码；跟踪密码、PIN、摘要、账号、URL 在消息、DOM 引用、缓存、日志和存储里的生命期。确认过期不仅禁止读取，还会释放引用。 |
| 权限与页面边界 | 对照 manifest 权限与调用点；检查 HTTPS、回环、普通 HTTP、嵌套 frame、导航换页、不可见/只读字段、OTP 以及多个候选账号。审查时不绕过这些边界。 |
| MV3 生命周期与正确性 | 对每个跨 `await` 的操作检查旧响应、取消、断连、切换标签、后台重启、重复提交和 TTL。对存储分别检查：缺省值、明确关闭、读取失败、写入失败，不能混为一谈。区分“请求已发送”“结果未知”“确已保存”。 |
| 协议与原生集成 | 查会话切换、身份核对、长度与编码、超时、序列化、迟到回复、错误映射及密钥生命周期。核对 helper 的动作白名单、浏览器识别、安装/升级/卸载对称性、系统设置副作用。不要改动本机配置来验证推测。 |
| 性能与资源 | 查每次键入是否扫描整个文档；数一次动作触发的消息、原生调用和存储写入。检查计时器、监听器、缓存、DOM 引用和后台队列是否释放。没有测量就不要宣称卡顿或节省了多少时间。 |
| 可用性与无障碍 | 只用键盘能否找到焦点、操作和退出？检查 PIN、账号输入、设置开关、错误提示、读屏播报、缩放、深浅主题及中英文一致性。逐句核对失败文案与用户实际可采取的动作。 |
| 交付与维护 | 对照根目录和 dist 的 manifest、资源和后台路径；查 bundle 是否新鲜、依赖与锁文件、CI 版本、安装文档、许可证和第三方归属。找重复规则、死分支及已删除工具的残留引用。不要仅因文件长就要求重构。 |
| 测试质量 | 对每项关键承诺，指出哪条断言能使错误实现失败。区分测真实业务逻辑与仅测 mock。重点查状态转换和失败路径，不追求测试数量。 |

## 验证约束

- 先读脚本再运行。项目依赖就绪时执行 `npm test`、`npm run check`、`npm run build`、`git diff --check`，分别记录结果。构建前后区分已有改动与本次生成改动；不要重置工作树。
- 对高影响发现，再独立找一个反证：是否已有前置校验、补偿写入、清理回调或权限限制？必要时用 `node:test`、Node 内置模块或 Python 标准库，用虚构数据在内存中模拟单个失败。不要启动浏览器、安装自动化框架、访问真实密码库、调用系统认证或打印凭据。
- 模拟器不能证明真实系统弹窗、读屏体验或保险库落盘。对必须在设备上观察的问题，写出最短人工核验步骤和预期结果，标记“未实机验证”，不要自行执行。

## 输出约定

先列最值得做的三项，再给完整发现和覆盖表。每项格式：**优先级｜触发条件 → 实际结果 → 用户影响｜文件:行号｜证据等级（已复现 / 源码可确认 / 待验证）｜最小修复｜验收方法**。同一根因只报一次。P1 用于凭据处理、数据丢失、严重授权或核心流程问题；P2 用于可恢复的错误和明显干扰；P3 用于一般维护或体验改进。另列已验证正常的关键路径、未覆盖项及原因。没有证据的优化想法放到候选区，不当成缺陷。不要把一次测试全绿称为“没有问题”。
